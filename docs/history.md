> This is the detailed engineering history, kept as it was written. Paths in it predate the move to `src/`: `Dev/Typedown.WinUI` is now `src/Caret.App` and `Dev/Typedown.Editor` is now `src/Caret.Editor`. For a short list of changes per version, see [CHANGELOG.md](../CHANGELOG.md).

# Caret Portable vs. Caret

Caret Portable was split off from [Caret](https://github.com/fegyenc/Caret) (commit `91f059c`) for PCs where applications can't be installed. What changed:

- **Unpackaged only.** No MSIX, Store identity or signing certificate. `Release` publishes a self-contained folder (the .NET runtime and Windows App SDK included) with `Caret.exe`. `Package.appxmanifest`, `PACKAGING.md`, `docs/store` and the MSIX deployment guides were removed.
- **Microsoft MarkItDown does every conversion.** The built-in .NET converters (`Services/Conversion`, Open XML SDK and PdfPig) were removed. `Services/MarkItDown` finds the user's Python without relying on PATH (`PythonLocator`) and runs MarkItDown in one worker process per batch (`MarkItDownWorker`, a JSON-lines protocol over stdin/stdout). The Convert page has a Converter panel that shows what was found and offers *Choose python.exe…*, *Detect again* and *Install MarkItDown*. The choice is stored as the `PythonPath` setting.
- **More formats**: .xls, Outlook .msg, HTML, EPUB, .ipynb, JSON, XML, RSS, TXT and ZIP, alongside Word, Excel, PowerPoint, PDF and CSV. The *Extract images* option went away, because MarkItDown doesn't write image files.
- **No PATH or registry changes.** The old MarkItDown installer added pip's Scripts folder to the user PATH. Now MarkItDown is always started as `python -c …` with the full path to python.exe, and installing it is just `pip install --user` into that Python.
- **Data next to the exe.** Settings, recent files, favorites, templates, backups and the WebView2 profile go to `Data\` beside `Caret.exe`. If that folder isn't writable, they go to `%LOCALAPPDATA%\Caret Portable`.
- **No update check.** The settings panel for it is hidden; updating means replacing the folder.
- **A tidy folder.** The app lives in `app\`, started by a small launcher `Caret.exe` (`Dev/Caret.Launcher`, .NET Framework 4.8). `Data\` and an optional `python\` go next to the launcher (`Config.PortableRoot`). `build/package.ps1` assembles the folder and drops the Windows App SDK's resource folders for languages other than English, French and Spanish (about 80).
- **Text encodings (1.0.1).** Brought over Caret's legacy code page fallback ([fegyenc/Caret#24](https://github.com/fegyenc/Caret/pull/24)): Markdown that isn't UTF-8 opens correctly, with "Markdown · Windows-1250" in the status bar until it's saved. For conversions, Caret now tells MarkItDown the encoding of CSV, TXT, JSON, XML and HTML files (`MarkItDownFormats.CharsetFor`, same rule: byte-order mark, strict UTF-8, else the ANSI code page) instead of letting it guess, which turned a French Windows-1252 CSV's "Été à Noël" into "Été ŕ Noël". CSVs separated by `;`, tab or `|` (Excel on French, Polish or Hungarian PCs) are rewritten with commas before MarkItDown sees them, since it only splits on commas and put each row in one cell. Verified against MarkItDown 0.1.8: Windows-1250 and -1252 CSVs, quoted fields containing `;`, tab-separated, UTF-8 with BOM, and TXT.
- **Separate single-instance key**, so the portable app doesn't hand its launch over to an installed Caret.
- **CI**: `.github/workflows/portable.yml` builds x64 and ARM64 zips on `windows-latest`, starts the x64 build from a fresh folder to check that the editor loads, and attaches the zips to a release when a `v*` tag is pushed.

# Caret vs. Typedown: what changed

Caret is a fork of [Typedown](https://github.com/byxiaozhi/Typedown), ported from WPF + XAML Islands on .NET Core 3.1 to native **WinUI 3 + WebView2** on **.NET 8** (`Dev/Typedown.WinUI`). The Markdown editor itself (`Dev/Typedown.Editor`, React/TypeScript) carried over as-is at first and has since picked up Caret-specific changes (split preview, image paths, formatting fixes), noted below. This document is mostly about the native host around it. The original WPF host (`Dev/Typedown`, `Dev/Typedown.Core`), its tests and tools were removed from this repo once the port was complete. Paths like `Typedown.Core\…` below and in source comments refer to the [upstream Typedown](https://github.com/byxiaozhi/Typedown) code.

Three things happen to each piece of the original as it crosses over:

- **Ported** — same behavior, same wire protocol to the editor, translated line-for-line where the old and new platforms allow it.
- **Reimplemented** — same end result, different mechanism, because WinUI 3 / Windows App SDK offers a more direct native way to do it than the original's WPF-era approach (or the original's exact mechanism isn't available at all outside XAML Islands).
- **Deferred** — not yet in `Typedown.WinUI`. Listed explicitly rather than silently dropped.

## Ported

- Core editing surface: the wire protocol between the native host and the editor (`PostMessage`/`RemoteInvoke`/`EventCenter`, the same message names and payload shapes) — traced against `Dev/Typedown.Editor/src/services` on the JS side
- Find & Replace, driven by the same Search/Find/Replace wire messages
- Settings persistence shape (JSON file, same property list) and the live SettingsChanged push for font size/line height/tab size/etc.
- AutoBackup: same hash-named backup file scheme, same recover/discard flow on load
- Recent files, folder workspace (ExplorerItem tree, live FileSystemWatcher updates), export (HTML/PDF/text) and print
- GetCurrentTheme/ThemeChanged payload shape (`{ theme, accentColor, background }`), including a wire-contract quirk in `theme.ts` where `accentColor` and `background` use different key casing — matched exactly, not "fixed," since that JS is unmodified

## Reimplemented against modern APIs

- **Window chrome**: `ExtendsContentIntoTitleBar` + `SetTitleBar` instead of a custom-drawn caption bar (the original's private `Typedown.XamlUI` package isn't available outside that repo)
- **Window placement**: `AppWindow`/`OverlappedPresenter` instead of raw `WINDOWPLACEMENT` P/Invoke
- **Mica backdrop**: `Window.SystemBackdrop` (`MicaBackdrop`/`MicaKind`) instead of the manual `WindowsSystemDispatcherQueueHelper` + `MicaController` compositor setup XAML Islands needed
- **Local image loading**: `CoreWebView2.WebResourceRequested` serves `file:///` image requests directly, instead of relying on Chromium loading `file://` from an `https://` virtual-host origin (it doesn't, regardless of `--disable-web-security`)
- **Native folder picker**: raw `IFileOpenDialog` COM interop on a dedicated STA thread — `Windows.Storage.Pickers.FolderPicker` throws `E_FAIL` reliably in this unpackaged app
- **Keyboard shortcuts while the editor has focus**: WebView2 owns a real child HWND, so XAML `KeyboardAccelerator`s never fire there — a small injected JS `keydown` listener forwards the relevant combinations back to the host instead
- **Single-instance activation redirection**: `Microsoft.Windows.AppLifecycle.AppInstance` (`Program.cs`) instead of the original's Mutex + `NamedPipeServerStream` handshake (`Typedown\App.cs`) — a second `Caret.exe` launch (e.g. double-clicking a `.md` file in Explorer) still hands off to the already-running instance instead of starting a new process, and either focuses an already-open window for that file or opens a new one in the existing process, same end result via the Windows App SDK's own purpose-built API instead of hand-rolled IPC. Needed replacing WinUI 3's SDK-generated `Main` with an explicit one (`DISABLE_XAML_GENERATED_MAIN`) so a redirected second launch never creates an `Application` or window in that second process at all.
- **Folder tree clipboard cut/copy/paste**: `Windows.ApplicationModel.DataTransfer.DataPackage`/`Clipboard` (`MainWindow.xaml.cs`'s "Folder tree clipboard & drag-drop" region) instead of the original's `System.Windows.Clipboard` plus a hand-rolled "Preferred DropEffect" byte blob (`Typedown\Services\FileOperation.cs`/`Clipboard.cs`) to distinguish Move from Copy — `DataPackage.RequestedOperation` does that natively, no marker format needed. The actual copy/move/delete still goes through the same shell engine as the original's raw `SHFileOperation` calls, via `Microsoft.VisualBasic.FileIO.FileSystem` (already this project's convention for Delete) instead of P/Invoking `SHFileOperation` directly — same Explorer-native conflict/overwrite prompts and Recycle Bin support.

## New since the fork

Not present in Typedown at all:

- **Live theme push accuracy fix**: the original's `GetCurrentTheme`/`ThemeChanged` payload shape was ported, but getting the accent/background color casing to actually match what `theme.ts` reads required building `background` as a raw JSON object rather than a reflected POCO — confirmed by inspecting the actual wire payload, not assumed
- **Multi-window support**: any number of windows in one process, focus-existing-window-instead-of-duplicate, process exits only when the last one closes
- **MSIX packaging** for `Release` builds — see [PACKAGING.md](PACKAGING.md). Verified through building, signing, and confirming Windows correctly refuses to install it without the dev certificate trusted first (trusting a certificate is a machine-level security-store change, so that step — and installing/launching the trusted package — is intentionally left for a human to run rather than automated here)
- **Warm-autumn rebrand**: a full visual reskin from a brand asset package (`design-system/design-tokens.json`) — new app icon/window icon/MSIX tile assets, a light/dark color theme (`Themes/Caret.xaml`) applied by overriding WinUI 3's own semantic resource keys (`TextFillColorPrimaryBrush`, `CardStrokeColorDefaultBrush`, `SystemAccentColor` + its Light/Dark variants, `ControlCornerRadius`/`OverlayCornerRadius`, ...) so it cascades into stock controls without touching their templates, and the folder tree's folder/file icons rebuilt as brand line-icon `Path` geometries instead of Segoe Fluent glyphs. Mica now defaults to **off** (`SettingsViewModel.UseMicaEffect`) — the brand background is a flat illustrated color field, and Mica's system-mixed translucent tint washed it out; the Settings toggle still turns it back on for anyone who prefers the glass look.
  - The asset package's `brand/app-icons/png/*.png` files were all corrupted — every size, every theme was actually the same cropped fragment of a presentation sheet (confirmed by inspecting pixel content, not just file names/dimensions). The SVG logo sources were clean, so the actual app icon/MSIX tile assets were rasterized from those instead, with a small purpose-built renderer (the SVGs only use a handful of path commands, no need for a full SVG engine).
  - Two WinUI 3 API traps hit and documented in code (`Themes/Caret.xaml`'s comments): `Shape.StrokeLineCap`/`StrokeStartLineCap`/`StrokeEndLineCap` aren't real dependency properties on `Microsoft.UI.Xaml.Shapes.Shape` (that's WPF-only) — setting either one crashes the XAML compiler's `MarkupCompilePass2` at build time with no diagnostic; and `{ThemeResource}` lookups don't resolve across sibling merged `ResourceDictionary` files — a key defined in one file's `ThemeDictionaries` crashes the native XAML engine at runtime (0xc000027b) if referenced from a `Style` in a *different* merged file, even for a standard key, not just a custom one. Both are silent, hard crashes rather than clean errors — same class of tooling fragility as the `[DoNotNotify]` Fody note already in `MainWindow.xaml.cs`.
- **Sidebar restructure** (Phase 2 of the warm-autumn reskin, on top of Phase 1's color/icon reskin): a real navigation sidebar above the existing folder tree — `+ New Note`, then Home/Recent/Favorites/All Files/Templates/Trash, matching the brand mockups' layout. Genuinely new features behind three of those, not just new panels on existing data:
  - **Favorites** (`Services/FavoritesService.cs`) — a starred-files list, same small-JSON-file shape as `RecentFilesService`. "Toggle Favorite" is on the file context menu; the sidebar panel lists them and cleans up a path that's since been deleted or renamed.
  - **Templates** — no separate service; the panel just lists `.md` files in a `Templates` folder under `Config.GetLocalFolderPath()`, so the folder itself is the persistence. "Save current document as template..." writes one; clicking one starts a new document pre-filled with its content via `FileViewModel.ApplyRecoveredBackup` (the same mechanism AutoBackup recovery already used) rather than opening the template file itself for editing.
  - **Trash** (`Services/TrashService.cs`) — explicitly *not* a reimplementation of the Recycle Bin: `DeleteContext_Click` already sends files there via `Microsoft.VisualBasic.FileIO.FileSystem`'s `RecycleOption.SendToRecycleBin`, and restoring from it is Explorer's job. This is a small log of what Caret itself deleted and when, so the sidebar entry has something more useful to show than a dead end; clicking an entry opens the real Recycle Bin (`explorer.exe shell:RecycleBinFolder`) to actually restore something.
  - "All Files" doesn't get its own panel — it just hides the others so the folder tree (already below, always shown once a folder's open) is what's visible. "Home" is a static welcome panel.
- **Title bar theme toggle**: a sun/moon `Button` sits directly inside the `SetTitleBar` element next to a Settings shortcut (the mockups' top-bar icon row) and still works as an ordinary click, not a drag handle — WinUI 3 detects interactive controls inside a title bar and excludes them from the drag region on its own, no extra passthrough setup needed. It's a plain binary switch (unlike the three-way Light/Dark/"Use system setting" `ComboBox` still in Settings), reads the *resolved* theme so a system-theme user's first click always visibly does something, and stays in sync with that Settings combo box since both just set the same `settings.AppTheme`.
  - Still not here: the layout-toggle icon from the mockups' top bar, and tabs — Caret is still one document per window. Converting that to tabs-in-one-window is a real architectural change (touches `FileViewModel`, per-document dirty/autosave/backup tracking, window-close-confirmation semantics) with real UX tradeoffs against the current multi-window model (e.g. dragging a document to a second monitor), not something to invent unilaterally — left for a follow-up with actual design input. The mockups' search box itself is now in — see below.
- **Real app-icon artwork**: the brand asset package's original `app-icons.zip` (used for Phase 1) turned out corrupted, so Phase 1 shipped with icons rasterized from a hand-built SVG stand-in; a clean re-export of that package arrived with genuine hand-tuned raster artwork per size (`light`/`dark`/`accent` variants at 16 through 1024px), so `logo.ico`, all `Square44x44Logo`/`Square150x150Logo`/`StoreLogo`/`Wide310x150Logo`/`SplashScreen` MSIX tile assets, and the root `logo.png` were all regenerated from that instead — `logo.svg` (the stand-in) is gone, since the asset package's own `master/README.md` is explicit that no vector substitute is the approved icon. `logo.ico` itself is a hand-rolled multi-frame ICO container (16/24/32/48/256px, each frame the artwork's own hand-tuned bitmap for that size, PNG-compressed) rather than one image resized by a library at save time, since Pillow's ICO writer only resamples from a single source image and would've thrown away the smaller sizes' hand-simplified detail.
  - Fixed in the same pass, found while eyeballing the result: the custom title bar (`ExtendsContentIntoTitleBar`) never actually showed an icon at all, `AppWindow.SetIcon()` notwithstanding — that call only reaches the taskbar/Alt-Tab, not the extended title bar's own content area, which needed a plain `Image` added to `AppTitleBar` like any other title bar element (`MainWindow.xaml.cs`'s `SetUpTitleBar`). That `Image` then rendered nothing at all with `VerticalAlignment="Center"` — confirmed with a solid-color `Rectangle` in its place, ruling out image decoding or position/size as the cause, root cause not fully understood — while `VerticalAlignment="Top"` plus a manual top margin (same visual result) renders correctly; the Buttons and title `TextBlock` sharing that row are unaffected and still use `Center` normally.
- **Quick Open ("Go to File")**: new since the fork, not in the original at all — a VS Code-style Ctrl+K file switcher, reachable via the mockups' title-bar search icon, `File > Go to File...`, or Ctrl+K itself (wired through both the normal XAML `KeyboardAccelerator` path and the WebView2 `HostShortcut` JS-forwarding path the other host shortcuts already use, so it works whether focus is in the sidebar or the editor). Lists every markdown file under the open folder — a plain recursive walk (`MainWindow.xaml.cs`'s `CollectMarkdownFiles`) rather than reusing the FileSystemWatcher-backed `ExplorerItem` tree, since Quick Open's candidate list is rebuilt fresh each time it opens and doesn't need to stay live — filtered by substring match as you type, not a real fuzzy-match algorithm (plenty for a project-sized file list). Falls back to Recent Files when no folder is open. Diverges from the folder tree's own filter in one deliberate way: also skips `bin`/`obj`, since `FileTypeHelper`'s markdown-extension set includes `.txt` (ported verbatim from the original, same set the tree itself uses) and a dev repo's build output otherwise buries real notes under `LICENSE.txt`/`FileListAbsolute.txt` noise — confirmed by opening this repo itself as the folder and seeing exactly that before adding the exclusion.
- **PDF export options**: the original had `PdfPrintSettings` (`Typedown.Core\Models\RuntimeModels\ExportPdfSettings.cs`) as C# state, but no host UI in this port ever let a user actually set any of it — `Export > PDF` just called `PrintToPdfAsync(path, null)`, taking every `CoreWebView2PrintSettings` default silently. One of those defaults turned out to be a real, concrete gap rather than a hypothetical one: `ShouldPrintBackgrounds` defaults to `false`, so every PDF export up to now has been dropping code-block background tints and any other background-color styling without anyone asking it to — confirmed against the WebView2 SDK's own XML docs, not assumed. A small "PDF Export Options" dialog now asks for orientation, page size (Letter/A4/Legal), background printing (on by default, fixing the gap above), and header/footer (off by default, since a `file://` path in the footer isn't useful) before the save picker opens. Margins and custom header/footer text aren't exposed — WebView2's own defaults there are reasonable and there's no concrete gap driving customizing them, unlike the four options that are exposed.
- **Import via MarkItDown**: genuinely new, no equivalent in the original at all — `File > Import via MarkItDown...` shells out to Microsoft's own [MarkItDown](https://github.com/microsoft/markitdown) CLI to convert Word/Excel/PowerPoint/PDF/images/audio/etc. into Markdown, opened as a new Caret document (same `NewFile` + `ApplyRecoveredBackup` flow the Templates panel already used, so it opens dirty/unsaved — a converted copy, not a link back to the source file). Deliberately a subprocess call against whatever `markitdown` the user has on `PATH`, not a vendored dependency: MarkItDown is a Python package with real native-library extras per format, and there's no .NET port of it, so bundling it would mean shipping a Python runtime inside a WinUI 3 app. The redirected stdout/stderr pipes are forced to UTF-8 on both the .NET and Python sides (`StandardOutputEncoding`/`PYTHONIOENCODING`) — without it, non-ASCII text silently corrupts, confirmed concretely rather than in theory: this machine's own file paths have accented Hungarian characters, and even the bare `markitdown` CLI mangled them through a redirected pipe before the fix.
  - **Self-install when `markitdown` isn't found**: the original failure path just printed a `pip install` command and left the user to run it themselves in a terminal — fine for a developer, a dead end for anyone else. Instead, Caret now offers to install it itself: finds a Python (`py -3`, falling back to `python`/`python3`), runs `pip install --user markitdown[all]`, then works out where pip actually put the executable (`python -m site --user-site`, `Scripts` is always its sibling in CPython's own layout — same convention on both a python.org install and the Microsoft Store package) and adds that folder to `PATH`, both for the already-running process (so the conversion that was just requested succeeds immediately, no restart) and persisted to the user's environment (so new terminals and future launches find it too). Verified against a real clean-state case, not just code review: launched the dev build with every Python folder stripped from its inherited `PATH` so `markitdown` genuinely wasn't resolvable, triggered the import, and watched it install via the machine's `py -3` (Python 3.13), land in `%APPDATA%\Python\Python313\Scripts` (not on `PATH` beforehand), and complete the original conversion — a real Hungarian/German-accented `.docx` — without ever leaving the app or opening a terminal.
- **Spellcheck**: `SettingsViewModel.SpellcheckEnabled`/`SpellcheckLang` already existed as dormant settings (carried over with the rest of the ported property list) but nothing ever read them. The editor itself has no spellcheck concept at all — `Typedown.Editor`'s Muya library defaults its own `spellcheckEnabled` option to `false`, with a comment from its original authors explaining why: "The browser is not able to correct misspelled words without a custom implementation." Rather than touch the editor's own source to flip that default, this sets the standard HTML `spellcheck` attribute from the host side (a small script injected via `AddScriptToExecuteOnDocumentCreatedAsync`, re-applied through a `MutationObserver` since Muya replaces its container element) — Chromium's built-in squiggly-underline detection reads that attribute regardless of who set it. Confirmed genuinely safe, not just assumed: Muya suppresses the native `contextmenu` event everywhere in the editor (right-clicking a misspelled word and right-clicking plain correctly-spelled text both show no menu at all), so there's no right-click-to-correct path that could desync from Muya's content-state model in the way the upstream comment warns about — the underline is all you get, cosmetic only, nothing to interact with. Opt-in (Settings > Spellcheck, default off) since it's a visible behavior change nobody asked for, not because of any risk. One real bug hit and fixed along the way: the injected script's `MutationObserver` setup ran at `AddScriptToExecuteOnDocumentCreatedAsync`'s document-start timing, before `document.documentElement` exists yet, throwing synchronously and silently killing the whole script before it ever applied the attribute once — caught via WebView2's DevTools console (`OpenDevToolsWindow()`, temporarily), not guessed; fixed by deferring the observer setup to `DOMContentLoaded`.
- **Status bar**: `SettingsViewModel.StatusBarOpen`/`WordCountMethod` were dormant the same way — ported from the original's property list but never read. The original WPF app's own `StatusBar.xaml` (`Typedown.Core\Controls\EditorControls\StatusBar.xaml`) is the real reference for what's shown, not the brand mockups' art: the mockups show a literal "Ln 18, Col 1" cursor position, which isn't reproducible against Muya — a block-based WYSIWYG editor with no line/column concept at all (that only exists in the CodeMirror source view, which isn't a real wired-up editing mode here; see the `SourceCode` toggle entry in Known Issues below). What the original app actually had, and what this ports: a bottom bar with a characters/words count that toggles between the two on click (`WordCountMethod`, 0/1, same two values as the original's `ComboBox`), sourced from the same `StateChange` `wordCount` payload (`{ word, character, paragraph, all }`, computed in `Typedown.Editor/src/components/Muya/lib/utils/index.js`) the table-of-contents pane already subscribes to — `UpdateWordCount` just rides the same subscription as the existing `UpdateToc`. A static "Markdown" label sits on the left, since every file Caret edits is one. `View > Status Bar` toggles it, same shape as the existing `View > Sidebar` toggle.
- **Sidebar footer illustration**: a small decorative card — "Ideas grow here." over autumn-leaf art — anchoring the bottom of the folder list, matching the brand mockups' sidebar. The mockups' own art there is a photorealistic lake/mountain scene that turned out not to actually be in the delivered asset package (checked directly, not assumed: only flat vector pieces exist — `leaves/*.svg`, `decorative/atmosphere/*.svg`; the manifest inside the newer `v2` package folder (`ASSET_MANIFEST.md`) lists a matching `artwork/sidebar/sidebar-*.svg` that would have been the exact asset, but that path doesn't exist on disk in either the extracted `v2` folder or the root `Caret_Assets_Package.zip` — presumably never actually delivered). So this is composed from the real assets that are there instead of approximating a photo: the same leaf silhouette path from `leaves/leaf-copper.svg`/`leaves/leaf-orange.svg` (copied verbatim into `MainWindow.xaml`, the same way `CaretLineIconStyle` already does for the folder/file tree icons), at two sizes and rotations, over a soft two-stop gradient using the theme's own surface colors — flat and illustrated, consistent with the rest of the brand pass rather than trying to force in a photo the app's actual visual language doesn't otherwise use (`UseMicaEffect` defaults off for the same "flat illustrated background" reasoning already in `Themes/Caret.xaml`). Purely decorative, no click handler; hides along with the rest of `TocPane` when Sidebar is toggled off.
- **Fixed: pasting into the editor could silently corrupt or lose the document.** User-reported, and reproduced exactly: pasting a multi-paragraph markdown block (e.g. copied from an AI chat) showed the raw `#`/`-`/backtick syntax literally instead of rendering, typing afterward inserted characters in the wrong place or dropped them outright, and further edits left the document in a visibly inconsistent state — some headings parsed, others didn't. Root cause: `Typedown.Editor` already has a complete, markdown-aware paste pipeline (`Muya/index.tsx` listens for a `'Paste'` message and routes it straight to `ContentState.pasteHandler` in `pasteCtrl.js`, which correctly turns pasted markdown/HTML into real blocks) — but nothing on the **host** side ever sent that message. Ctrl+V was never intercepted, so WebView2's own native contenteditable paste ran instead, which just dumps the pasted text as a raw string into whatever single block the cursor was in, with no markdown parsing at all — exactly the kind of DOM/model desync that's caused data loss elsewhere in this port (see the `SourceCode` toggle entry below). Fixed on the host side only, same as the rest of this port's convention of treating the editor bundle as unmodified: `Ctrl+V` is now added to the existing keydown-interception script (`HostShortcutScript`, the same mechanism `Ctrl+S`/`Ctrl+O`/etc. already use, since WebView2 swallows XAML `KeyboardAccelerator`s), which forwards to a new `PasteFromClipboard` that reads both plain text and HTML off the Windows clipboard (`Windows.ApplicationModel.DataTransfer.Clipboard`, `HtmlFormatHelper.GetStaticFragment` to unwrap the raw `CF_HTML` header format into the clean HTML `pasteCtrl.js` expects) and posts it as `{ type: "normal", text, html }` — the exact shape the JS side was already waiting for. Verified against the exact repro: the same multi-paragraph paste now renders correctly (real headings, bullets, a syntax-highlighted code block, live links, all four headings picked up in the TOC pane immediately), and typing afterward lands exactly where expected.
  - **AutoSave no longer writes a blank editor over a real file.** The paste bug above didn't lose the reporter's contacts on its own. It left the editor reporting an (almost) empty document, AutoSave wrote that over the real file within 5 seconds, and the recovery backup deleted itself because `BackupTick` threw away any backup once the buffer went blank. Three changes, all in the host: `FileViewModel.WouldBlankSavedFile` (buffer is blank but the last saved text wasn't) makes the AutoSave tick skip the save and log `AutoSave: skipped blanking '<path>'` once. `BackupTick` now only deletes a backup when the buffer matches disk again, not when it merely went blank while still dirty. The unsaved-changes prompt spells out "saving will erase its contents on disk" in that case and makes **Don't Save** the default button, so Enter can't wipe the file by reflex. An explicit Ctrl+S still saves a blank document, since that's the user's choice. Verified in the dev build: with AutoSave on, typing a real edit auto-saved normally, then emptying the editor left the file on disk untouched across two AutoSave ticks, and the prompt showed the warning with Don't Save as the default.
  - **Undo/Redo** (Ctrl+Z, Ctrl+Y / Ctrl+Shift+Z, and new Edit menu items). Same root cause as paste: the editor (Muya) has no undo of its own. The original app kept the history on the host (`Typedown.Core`'s `ContentHistory` + `EditorViewModel.Undo/Redo`) and restored a snapshot by sending `SetMarkdown { text, cursor }`, which the editor still listens for (`Typedown.Editor/src/components/Editor/index.tsx`). That host half was never ported, so Ctrl+Z fell through to the browser's native contenteditable undo, editing the DOM behind Muya's model. `Models/ContentHistory.cs` is a straight port (logic unchanged: 100 steps; a burst of typing commits after 3s idle or when the cursor moves to another line), fed from the editor's `FileLoaded`/`MarkdownChange`/`CursorChange` messages. History resets on every document load, so undo can never pull text from a previous document into a new one. `FileViewModel.ReplaceBuffer` updates the tracked text immediately on undo, so Save/AutoSave can't write the pre-undo text while the screen shows the undone one. The Edit menu shows the shortcuts as text only (`KeyboardAcceleratorTextOverride`), not as XAML accelerators, which are window-wide and would steal Ctrl+Z/Ctrl+A from the Find and Quick Open boxes.
  - **Select All (Ctrl+A) and Copy (Ctrl+C) go through the editor's own `SelectAll`/`Copy`**, as in the original. Copy now puts the selection on the clipboard as markdown (e.g. `# Heading`, `- item`) plus HTML, via a host `SetClipboard` handler (ported from `EditorViewModel.OnSetClipboard`) that was never registered; it also `Flush`es so the text survives Caret closing. **Cut stays native** on purpose: the editor's own Cut (`cutHandler` → `partialRender`) reproducibly left a removed paragraph on screen that was no longer in the document, while the browser's cut is reconciled correctly by Muya's input handler. (An earlier note here claimed native Ctrl+A → Delete didn't report the edit. That was wrong: it was reported, and swallowed by the bug below.)

It only sometimes does (confirmed in the log: `FileLoaded` with no echo after opening a file). ## Deferred

Called out here rather than silently missing:

- **Store submission** — the MSIX package is signed with a self-signed certificate, so installing a GitHub Release means trusting that certificate first (an admin step). A Microsoft Store listing (Store-signed) or a real code-signing certificate would remove that step.
- Export/Import config UI (image upload targets, per-format options beyond PDF's) and rebindable keyboard shortcuts (see the read-only reference above for why that's a much bigger feature than it sounds — the original's own shortcut settings were never functional in this port to begin with).

## Known issues

- **Folder tree item-to-item drag-and-drop** (dragging a row onto a folder row to move it) is implemented — `CanDrag`/`DragStarting`/`AllowDrop`/`DragOver`/`Drop` on each `TreeViewItem` in `MainWindow.xaml`, structurally the same per-item pattern the original's `FolderPage.xaml` used — but could **not** be confirmed working end-to-end. Log instrumentation showed `DragStarting` firing and setting valid drag data, and `DragOver` correctly accepting the first folder row the pointer crossed, but no further `DragOver` and no `Drop` at all afterward, reproduced identically across three different synthetic-input methods (an automation tool's mouse drag, raw Win32 `SendInput`, and a version with a custom minimal `DragUI` bitmap to rule out a rendering red herring). Cut/Copy/Paste from the context menu is the verified, reliable way to move or copy files in the tree in the meantime; drag-and-drop needs checking with a real mouse before it can be called done.
- **Update: no longer reproduces, and the Code view has shipped (see View / Code / Split above).** Retested after this session's fixes: edit in Code then back to View kept the edit (and it reached disk), and four Code↔View switches on the 42 KB CHANGES.md left the file byte-identical. Several fixes since touch this path (the first-edit-marked-saved bug, host message routing), but which one resolved it wasn't isolated, so the original report is kept below. **Original report: `settings.SourceCode` (the raw-markdown/CodeMirror view) loses document content when toggled** — tried and pulled back out, not shipped. The setting itself was already fully wired end-to-end from a previous pass (it's in `SettingsViewModel`'s live-push `notifySet`), so a title-bar button that just flipped it seemed like a safe, small addition; testing it against the real running app said otherwise. First toggle to source view renders completely blank (no line content, gutter only) regardless of light/dark theme; toggling back to WYSIWYG doesn't recover it either — confirmed via the wire log, not just visually, that the very next `MarkdownChange` the editor sends back is `{"text":"\n"}`, i.e. the editor's own tracked document is actually empty at that point, not merely failing to paint. Reproduced from a clean launch with a single toggle, so it's not an artifact of any other testing in the same session. Given a title-bar icon is exactly the kind of control someone clicks without expecting a destructive result, shipping it wasn't worth the risk — the editor bundle is treated as unmodified per this project's own convention, and whatever's wrong lives inside it (CodeMirror mount/state-sync territory), not in anything `MainWindow.xaml.cs` controls. Reproducing it again just needs a button or menu item that sets `settings.SourceCode = true` (one line — the setting already pushes live, nothing else to wire); the actual bug to chase from there is `Typedown.Editor`'s Muya→CodeMirror mode-switch path, not a host-side one.
